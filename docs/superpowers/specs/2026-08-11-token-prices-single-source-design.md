# Прайс токенов: один владелец вместо четырёх копий — дизайн

Дата: 2026-08-11
Статус: согласован, готов к плану реализации

## Задача

Сделать бэкенд единственным владельцем цен на токены и подключить к нему всех
потребителей: витрины приложения, контроллер оплаты, начисление и лендинг
linkeon.io.

## Зачем — повод, а не теория

Прайс размазан по четырём местам в двух репозиториях, и каждое добавление
тарифа превращается в лотерею «все ли копии нашли». Лотерея уже проиграна
дважды:

**08.04.2026.** Пакета `starter` не было в карте `tokensForPackage`. Сработал
откат `amount × 1000`, и десять человек получили по 149 000 токенов вместо
50 000.

**11.08.2026.** Тарифы `business` и `maximum` доехали до витрины, оферты и карты
токенов, но не до таблицы цен в контроллере оплаты. Нажавший «Бизнес» за
4 990 ₽ получил бы счёт на 149 ₽ и 50 000 токенов вместо 3 000 000 — молча:
платёж проходит, токены начисляются, ошибки нет. Дефект прожил на проде около
сорока минут; спасло только то, что за это время никто не покупал.

Второй случай особенно показателен: три копии из четырёх были согласованы между
собой, и ни один из существующих сторожей расхождения не увидел. Проверять
согласованность файлов внутри репозитория недостаточно — надо проверять, что
показывают и продают человеку.

## Где сейчас живут копии

| Место | Что хранит |
|---|---|
| `spirits_front/src/config/tokenPackages.ts` | цена, объём, ярлык скидки, ключи i18n |
| `spirits_back/src/payments/payments.controller.ts` | `package_id → сумма счёта` |
| `spirits_back/src/payments/payments.service.ts` | `package_id → объём начисления` |
| `land_linkeon/src/components/sections/Pricing.tsx` | цена, объём, ярлык скидки |

Плюс перечисление цен прозой в оферте `LegalModal.tsx` — оно остаётся
рукописным по отдельному решению проекта и здесь не меняется.

## Архитектура

### Бэкенд владеет цифрами

Новый модуль `spirits_back/src/payments/packages.ts`:

```ts
export interface TokenPackage {
  id: string;          // starter | extended | professional | business | maximum
  priceRub: number;
  tokens: number;
  /** Ярлык скидки в процентах, округлён вниз до пятёрки. Нет у базового. */
  savingsPct?: number;
}

export const PACKAGES: TokenPackage[];

/**
 * Исторические псевдонимы витрин. Отдельно от прайса: нужны для совместимости
 * со старыми клиентами, но тарифами не являются и наружу не отдаются.
 */
// basic → starter, standard → extended, premium → professional
export const ALIASES: Record<string, string>;
```

Три потребителя внутри бэкенда переводятся на него:

| Потребитель | Что берёт | Что было |
|---|---|---|
| `yookassa/create-payment` | сумму счёта | своя `pkgMap` |
| `tokensForPackage` | объём начисления | своя карта |
| `payments/methods` | ответ наружу | отдавал `packages: []` для рублей |

Это схлопывает три копии в одну внутри бэкенда — то, чего не хватило 11.08.

### Нового эндпоинта нет

`GET /webhook/payments/methods` уже существует, уже публичный (без гарда —
страница `/tokens` открывается по прямой ссылке с лендинга неавторизованным
гостем), уже вызывается обеими витринами и уже отдаёт массив `packages`. Для
рублёвого пути он намеренно пуст:

```ts
// Пакеты отдаём только для крипто-витрины: рублёвые зашиты на фронте.
packages: useCrypto ? this.priem.packages() : [],
```

Достаточно его заполнить. Ноль новых ручек, один запрос вместо двух, а
комментарий про ограничение превращается в описание нормы.

Валютные пакеты «Приёма» остаются отдельной структурой: у них своя экономика
(комиссия сети не зависит от суммы, порог оплаты картой $10), и слияние в одну
таблицу потеряло бы эти отличия.

### Витрина приложения

`spirits_front/src/config/tokenPackages.ts` теряет цифры и оставляет подачу:

```ts
export interface PackagePresentation {
  id: string;
  nameKey: string;
  popular?: boolean;
}
```

Цены, объёмы и проценты приходят из ответа `payments/methods`. Карта названий
валютных пакетов `CRYPTO_NAME_KEY` остаётся как есть.

Поле `amountKey` из нынешнего модуля **удаляется**: проверено — его не читает ни
один компонент, только собственный тест. Оно закладывалось под таблицу тарифов,
но та осталась рукописной с прямыми вызовами `t()`, так что поле мертво со дня
появления. Сами ключи локалей (`payment.info.package_business_amount` и
соседние) живы и используются в таблице напрямую — удаляется указатель, не
строки.

Согласованность объёма на карточке витрины обеспечена устройством, а не
проверкой: карточка показывает число через `formatTokens(pkg.tokens)`, то есть
берёт его из тех же данных, что и цену. Расходиться нечему.

**При недоступном API витрина показывает состояние ошибки с повтором** — не
пустоту и не зашитый резерв. Резерв был бы новой копией, которая разойдётся, а
показать неверную цену хуже, чем не показать никакой. Практического ухудшения
нет: API и так нужен этой странице для баланса и создания платежа, при его
недоступности покупка невозможна в любом случае.

### Лендинг

`land_linkeon/scripts/prerender.mjs` получает шаг: сходить за прайсом и передать
его в рендер, чтобы цены попали в статический HTML на всех семи выпущенных
языках. `Pricing.tsx` теряет свой `PACKAGES` и принимает данные снаружи.

Почему на сборке, а не в рантайме: лендинг пререндерится, и рантайм-запрос убрал
бы цены из статики — краулер увидел бы пустой блок. Плюс `my.linkeon.io` живёт
за прокси, обязательным для России, и рантайм-зависимость дала бы посетителю
секцию цен без цен.

**Если прайс на сборке не пришёл — сборка падает.** Собрать лендинг со старыми
ценами или без них молча — ровно тот тихий отказ, от которого вся эта работа.

Вместе с прайсом на лендинг приезжают тарифы «Бизнес» и «Максимальный», которых
там сейчас нет. Отдельной задачи на это не нужно.

## Сторожа

Три уровня, каждый ловит свой класс расхождения.

### Инварианты прайса — тест бэкенда

Переезжают туда, где теперь живут цифры:

- ожидаемая таблица `id → цена → объём`, выписанная явно;
- цена за 1000 токенов строго убывает по линейке;
- ярлык скидки не превышает фактическую выгоду и кратен пяти.

Главное следствие архитектуры проверять не нужно: контроллер и
`tokensForPackage` больше не могут разойтись, потому что читают одну структуру,
а не две одинаковые.

### Согласованность языков — юнит-тест фронта

Существующий `documentPrices.test.ts` меняет предмет. Цен в модуле не будет,
сверять с ними нечего — зато он продолжит проверять то, для чего цены не нужны:
русский и английский блоки оферты и таблицы тарифов перечисляют **один и тот же
набор пакетов**. Это ловит «забыл дописать в английский блок» сразу в редакторе.

### Согласованность системы — smoke

Приложение — SPA: текст оферты приходит не в HTML, а внутри JS-бандла, поэтому
HTTP-проверка страницы его не увидит. Но пара «объём — цена» лежит в бандле
литеральной строкой.

Проверка второго слоя smoke: взять цены из `payments/methods`, скачать бандлы
развёрнутого фронта и убедиться, что для каждого пакета встречается строка вида
`3 000 000 токенов — 4 990 ₽`. Без браузера, секунды на прогон.

Ловит именно тот класс, что прошёл мимо всех проверок 11.08: расхождение между
тем, что продаёт бэкенд, и тем, что обещает выложенный текст. Падает на фазе
`test.linkeon.io`, то есть прод не тронется.

## Порядок выката

Три репозитория, и порядок важен, иначе витрина останется без цен.

1. **Бэкенд** — модуль, потребители, заполненный `payments/methods`. Обратная
   совместимость полная: старые витрины продолжают работать на своих зашитых
   ценах и просто игнорируют новое поле.
2. **Фронт** — витрины переходят на ответ API. К этому моменту бэкенд уже отдаёт
   цены.
3. **Лендинг** — отдельный репозиторий со своим выкатом.

Между шагами система остаётся работоспособной.

## Риски

**Витрина остаётся без цен, если выкатить фронт раньше бэкенда.** Снимается
порядком выката: заполненный ответ появляется первым и до перехода витрин
никем не читается.

**Сборка лендинга становится зависимой от доступности прода.** Это осознанная
цена за цены в статике. Падение сборки заметно сразу, в отличие от молча
разошедшегося прайса.

**Оферта остаётся рукописной.** Подставлять в обязывающий документ цифры из API
нельзя, и это не меняется. Согласованность держит smoke-проверка.

## Вне объёма

- Перенос прайса в таблицу `token_packages` ради смены цен без выката. Таблица
  создана и пуста; API после этой работы не изменится, поэтому переезд можно
  сделать отдельной задачей, и потребители его не заметят.
- Валютная линейка «Приёма» — остаётся отдельной структурой.
- Восемь мест, где `SUM(amount)` складывает рубли с долларами в аналитике.
