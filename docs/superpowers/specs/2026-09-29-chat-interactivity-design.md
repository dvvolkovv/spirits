# Интерактивность чата: ход работы ассистента и уточняющие вопросы — дизайн

**Дата:** 2026-09-29
**Затрагивает:** `spirits_back` (`chat.controller.ts`, `chat.service.ts`, новые `chat/activity-map.ts` и `chat/ask-rule.ts`), `spirits_front` (`ChatInterface.tsx`, новые компоненты хода работы и карточки вопроса, локали ×7). Релей r.linkeon.io **не меняется**.

## Задача

Владелец: «нам бы добавить интерактивности побольше в чате с ассистентами как в claude code — уточняющие вопросы с возможностью выбрать, показывать не только три точки, а что реально сейчас делает ассистент решая задачу».

Решения владельца (29.09.2026):

1. **Ход работы — списком шагов.** Во время работы видны шаги, после ответа они сворачиваются в строку «3 шага · 42 с», которую можно раскрыть. В базе шаги не хранятся: после перезагрузки страницы их нет.
2. **Вопросы задают все ассистенты, по ситуации.** Одно общее правило в промпте. В личных и эмоциональных темах вариантов не предлагаем.
3. **Карточка вопроса — как в Claude Code.** До 3 вопросов в карточке, у каждого 2–4 варианта, выбор одного или нескольких, всегда есть «Свой вариант».

Канал — только веб (включая Capacitor-сборку `io.linkeon.app`: она грузит этот же фронт). Flutter, TG-бот и голос не меняются.

## Что есть сейчас

- **Релей уже сообщает о каждом вызове инструмента.** `server.mjs` на 5.101.115.184 (проверено на живом файле 29.09.2026, строка 716) на каждый `tool_use` в ответе CLI пишет SSE-событие `{"type":"tool","tool":"<имя>","input":"<JSON аргументов>"}`. `input` обрезан до 300 символов, поэтому **часто это невалидный JSON** (у `Write` аргумент `content` длинный).
- **Бэк это событие выбрасывает.** Разбор потока релея в `streamUniversalAgent` (`chat.service.ts`) знает только `delta`/`text`/`notice`/`result`/`done`. Клиенту уходят `begin`/`item`/`ping`/`end`. Такой же разбор, отдельной копией, есть в `upload-and-chat` (`chat.controller.ts`).
- **Маша (agent 3) идёт мимо релея**: локальный CLI, ответ приходит одним `item` в конце хода. `ClaudeCliService` с `onProgress` отдаёт события `{kind:'tool_use', name}` без аргументов. Из инструментов у Маши только продукты.
- **Фронт:** пока нет текста, `StreamingMessage` (`ChatInterface.tsx`) показывает три прыгающие точки. Кнопки `{{button:…}}` из `customMarkdown.tsx` умеют только навигацию (`buy-tokens`, `profile`, …). Ответить выбранным вариантом нечем.
- **Ограничение со стороны Flutter.** Мобилка ходит в тот же `/webhook/soulmate/chat` и берёт `content ?? text ?? delta` из **любого** события, кроме `begin`/`end` (`lib/services/chat_service.dart`). Событие с таким полем вклеилось бы в текст ответа. История чата и сессия на релее у веба и мобилки общие.

## Согласование возможностей клиента

Веб в теле `POST /webhook/soulmate/chat` и `POST /webhook/agent/upload-and-chat` передаёт (в загрузке — тоже обе возможности):

```json
"ui": { "activity": true, "ask": true }
```

`upload-and-chat` принимает multipart, поэтому там `ui` приходит строковым полем формы с тем же JSON (`{"activity":true}`). Контроллер разбирает его в `try`, а мусор считает отсутствием поля. 

Контроллер читает только строгие `true`. Всё остальное, включая отсутствие поля, означает «клиент этого не умеет». Мобилка, старые сборки веба и smoke-раннеры поле не шлют, поэтому ни новых событий, ни нового правила в промпте не получат. `streamChat` получает последним параметром `ui: { activity: boolean; ask: boolean }`, по умолчанию оба `false`.

## Часть 1. Ход работы

### Событие для клиента

```json
{"type":"activity","kind":"web_search","detail":"аренда офиса Казань"}
```

- `kind` — код шага из таблицы ниже. Текст шага собирает фронт через i18n, поэтому шаги показываются на всех семи языках.
- `detail` — необязательная уточняющая строка: не длиннее 80 символов, без переводов строк.
- **Полей `text`, `content`, `delta` в событии нет и быть не должно.** Иначе Flutter вклеит шаг в ответ. Тест проверяет это на каждом `kind`.
- Шлётся только при `ui.activity === true`, через тот же `safeWrite`, что и `item`.

### Перевод инструмента в шаг

Чистая функция `toActivity(toolName, rawInput, { userId, assistantId })` в `chat/activity-map.ts` возвращает `{ kind, detail? }` или `null` (шаг не показываем). Команды, пути, телефоны и прочая служебная информация наружу не уходят.

| Инструмент | `kind` | `detail` | Текст на фронте (ru) |
|---|---|---|---|
| `WebSearch` | `web_search` | `query` | Ищу в интернете · {detail} |
| `WebFetch` | `web_fetch` | только хост из `url` | Читаю страницу · {detail} |
| `Read` из папки загрузок | `read_upload` | имя файла (правила ниже) | Читаю ваш файл · {detail} |

**Разбор `input`.** Сначала `JSON.parse`. Если строка обрезана и не разбирается, нужное поле достаём регуляркой `"<ключ>"\s*:\s*"((?:[^"\\]|\\.)*)"` с разэкранированием. Если поля нет или оно оборвано посередине, шаг показываем без `detail`.

**Имя файла.** Берём только базовое имя и только из `/tmp/agent-uploads/` или `/tmp/agent-output/`; для любого другого пути (скрипты релея, домашние каталоги) шаг идёт без `detail`. Релей кладёт загрузку как `<ключ сессии>_<имя>` (`relay-agent/paths.mjs`, `uploadFileName`) и заменяет всё, кроме `[a-zA-Z0-9._-]`, на `_`. Поэтому префикс срезается по ключу сессии релея, который знает бэк. Кириллическое имя после релея превращается в подчёркивания («выписка.pdf» → `_______.pdf`), поэтому имя загрузки без латинских букв и цифр или с `__` не показываем: шаг звучит просто «Читаю ваш файл». Если в имени остался `userId` (телефон или UUID), `detail` не отдаём.

**Общее правило для `detail`:** не длиннее 80 символов (обрезка с «…»), переводы строк заменяются пробелом, строка с `userId` внутри отбрасывается целиком.

### Где бэк шлёт шаги

1. `streamUniversalAgent`: новая ветка `ev.type === 'tool'` в разборе потока релея.
2. `upload-and-chat` в контроллере: та же ветка в его копии разбора. Чтение большого PDF — ровно то место, где пользователь дольше всего смотрит на точки.
3. Путь Маши: `onProgress` → `toActivity(ev.name, '')`. На практике это шаг `product`.

### Как это выглядит на фронте

Компонент `ActivitySteps.tsx` и чистая логика шагов `turnActivity.ts`. Компонент назван не `TurnActivity.tsx`: на маке ФС нечувствительна к регистру, и импорт `./TurnActivity` нашёл бы `turnActivity.ts`.

- **Пока нет ни шагов, ни текста** — вместо трёх точек строка «Думает · 5 с» с идущим таймером от момента отправки.
- **Пришёл шаг** — список шагов в пузыре ассистента над текстом. Текущий шаг с индикатором, предыдущие с отметкой «сделано», в углу общий таймер.
- **Шаг считается сделанным**, когда пришёл следующий шаг, пошёл текст ответа или ход закончился. Успешно ли отработал инструмент, мы не знаем: результатов релей не присылает. Поэтому отметка нейтральная серая галочка, а не зелёная.
- **Склейка:** подряд идущие шаги с одинаковыми `kind` и `detail` сливаются в один со счётчиком («Обрабатываю данные ×6»). Двадцать вызовов `Bash` не превращаются в двадцать строк.
- **Ход закончился** — список сворачивается в строку «▸ 3 шага · 42 с» над ответом, по нажатию раскрывается. Если шагов не было (обычный разговор), после ответа не остаётся ничего: строка «Думал 8 с» над каждым ответом психолога была бы шумом.
- **Хранение:** у завершённого `Message` появляется необязательное поле `activity?: { steps; durationMs }`, только в памяти. Поллинг истории (`selectNewPolledMessages`) лишь дописывает новые сообщения и локальные не заменяет, поэтому шаги живут до перезагрузки или смены ассистента.
- **Множественное число** («1 шаг / 3 шага / 5 шагов») — ключи i18next `_one`/`_few`/`_many`/`_other` строго по категориям `Intl.PluralRules` каждого языка, а не копией из русского.

## Часть 2. Уточняющие вопросы

### Формат

Ассистент пишет в ответе блок кода с языком `ask` и JSON внутри:

````
```ask
{"questions":[
  {"header":"Для кого","question":"Для кого поздравление?","multi":false,"options":["Коллеге","Руководителю","Другу"]},
  {"header":"Тон","question":"Какой тон?","multi":true,"options":["Тёплый","С юмором","Деловой"]}
]}
```
````

- `questions` — от 1 до 3.
- `question` — обязателен. `header` — необязательная короткая подпись, ею начинается строка ответа.
- `options` — от 2 до 4 строк.
- `multi` — по умолчанию `false`.
- «Свой вариант» фронт добавляет сам, в JSON его нет.

Блок живёт в тексте сообщения, поэтому сохраняется в `custom_chat_history` как есть. Санитайзеры бэка (`stripLeakedToolSyntax`, `stripToolTags`) блоки кода не трогают, проверено. Карточка восстанавливается из истории после перезагрузки. База, миграции и релей не меняются.

**Почему не инструмент MCP, как в Claude Code.** Инструмент `ask_user` пришлось бы добавить в `allowedTools` релея. Релей выкатывается вручную, а рестарт обнуляет `--resume` всем пользователям. Ещё понадобились бы таблица, миграция на проде (там сломан migrate-runner) и эндпоинт. Это втрое больше работы ради той же карточки.

### Разбор на фронте

Новый модуль `utils/askBlock.ts` работает по образцу `parseCustomMarkdown`: заменяет блоки маркерами `__ASK_<n>__` и отдаёт карту разобранных вопросов.

- Открывающая строка — ` ```ask `, без учёта регистра, пробелы вокруг допустимы.
- **Незакрытый блок во время стрима** — всё от открывающей строки до конца текста заменяется заглушкой «Готовлю вопрос…». В готовом сообщении незакрытый блок разбирается до конца текста.
- **Мягкая проверка:** вопрос с пустым текстом или с меньше чем 2 вариантами отбрасывается, из годных берём первые 3; вариантов — первые 4, повторы схлопываются.
- **Битый JSON или ни одного годного вопроса** — показываем обычным текстом: вопрос и маркированный список вариантов, насколько их удалось достать. Сырой JSON пользователь не видит никогда.
- Если блоков в сообщении несколько, у каждого своя карточка на своём месте в тексте.

### Карточка `AskCard`

- Варианты — чипы, плюс чип «Свой вариант», который раскрывает поле ввода внутри карточки.
- **Один вопрос с одиночным выбором:** нажатие на чип сразу отправляет ответ.
- **Иначе:** чипы переключаются, «Свой вариант» в одиночном выборе заменяет выбранный чип, в множественном добавляется к ним. Кнопка «Ответить» активна, когда на каждый вопрос есть ответ.
- **Текст ответа** (`buildAskAnswer`):
  - один вопрос — выбранное через «, » («Коллеге» или «Тёплый, С юмором»);
  - несколько вопросов — по строке на вопрос: `<header или question>: <выбранное>`.
- Отправка идёт тем же путём, что набранное сообщение (`sendMessageText`). Очередь, проверка баланса и `turnBusy` действуют как обычно.
- **Карточка активна**, только если это последнее сообщение ассистента, после него нет сообщения пользователя, оно не стримится и не идёт ход (`isTyping`). В остальных случаях карточка неактивна.
- **Подсветка после ответа:** `parseAskAnswer` сверяет следующее сообщение пользователя с тем же форматом и подсвечивает совпавшие варианты. Подсветка «по возможности»: если человек ответил своими словами или в варианте есть запятая, подсвечено может быть не всё. Карточка при этом всё равно неактивна.

### Правило в промпте

`chat/ask-rule.ts`, константа `ASK_RULE`:

````
--- УТОЧНЯЮЩИЕ ВОПРОСЫ С ВАРИАНТАМИ ---
• Если без ответа пользователя хорошо не сделать, а ответ укладывается в 2–4 чётких варианта (формат, срок, для кого, какой тон), задай вопрос карточкой — блоком кода с языком ask:
```ask
{"questions":[{"header":"<1–2 слова>","question":"<вопрос>","multi":false,"options":["<вариант>","<вариант>"]}]}
```
• В блоке не больше 3 вопросов, у каждого 2–4 коротких варианта. multi: true — если можно выбрать несколько.
• Если твои инструкции разрешают только один вопрос за сообщение — в карточке тоже один вопрос.
• Один блок на ответ, в самом конце. После блока ничего не пиши и жди ответа.
• Вариант «Свой вариант» добавляется сам — не пиши его.
• Вопросы и варианты — на языке ответа.
• Не используй карточку в личных, эмоциональных и открытых вопросах («что вы чувствуете», «расскажите подробнее») — там спрашивай обычным текстом.
• Не спрашивай то, что уже известно из разговора или профиля. Если можно сделать хорошо без уточнения — делай.
````

- Добавляется **только при `ui.ask === true`** и **в системный промпт, а не в реплику.** Релей резюмит сессию через `--resume`, и всё, что лежит в реплике, копится в ней на каждом ходе: 900 символов × 44 хода — ровно то раздувание, с которым боролись 30.08. Системный промпт при `--resume` применяется заново и кэшируется.
- Путь релея — в `buildRelayStablePrefix` (опция `ask`). Загрузка файла получает правило тем же способом через `buildUploadHandoff`: у неё с текстовым ходом одна сессия, и системный промпт обязан совпадать.
- Маша — в `system` вызова CLI, до хвоста языка. У Маши в промпте есть приоритетное правило «не больше одного вопроса в сообщении». Строка «если твои инструкции разрешают только один вопрос — в карточке тоже один» снимает противоречие без особых случаев в коде.
- Последней строкой промпта по-прежнему остаётся языковая директива.
- Голосовой путь (`generateAgentReplyWithCharge`) — нет: TTS зачитал бы JSON.

## Риски

- **Мобилка увидит блок.** Сессия на релее и история у веба и мобилки общие. Ассистент, который отвечал блоками в вебе, может написать блок и в мобилке, а старые карточки из веба видны в истории мобилки. Flutter покажет их блоком кода: некрасиво, но вопрос и варианты читаются. Если захотим, коллега добавит отрисовку по формату из этой спецификации.
- **Ассистенты начнут спрашивать слишком часто.** Через неделю после выката проверить долю ответов с блоком по ассистентам. Тестовые аккаунты — список из `common/test-users.ts` на момент проверки:

  ```sql
  SELECT agent,
         count(*) FILTER (WHERE content LIKE '%```ask%') AS with_ask,
         count(*) AS total
  FROM custom_chat_history
  WHERE sender_type = 'ai'
    AND created_at > now() - interval '7 days'
    AND split_part(session_id, '_', 1) <> ALL (ARRAY['70000000000','79030169187','79169403771','79656445804'])
  GROUP BY agent
  ORDER BY with_ask DESC;
  ```

  Если доля заметная, ужесточить правило.
- **Рост промпта:** около 900 символов в системном промпте веб-ходов; в сессии не копится. Переход между вебом и мобилкой в одной сессии один раз промахивается мимо кэша префикса.

## Тесты

**Бэк (jest):**
- `activity-map.spec.ts`:
  - у каждого инструмента из `allowedTools` релея и из TalerID/продуктов есть свой `kind`, неизвестный идёт в `other`;
  - `sleep` даёт `null`;
  - обрезанный `input` у `Write`/`WebSearch` всё равно отдаёт имя или запрос;
  - `WebFetch` отдаёт только хост;
  - `detail` не длиннее 80 символов и никогда не содержит `userId` (телефон и UUID), префикс загрузки срезан;
  - путь вне папок загрузок и результатов не даёт `detail`;
  - в результате нет ключей `text`/`content`/`delta`.
- `chat.service`:
  - событие релея `tool` превращается в `activity` только при `ui.activity`;
  - правило про вопросы есть в промпте только при `ui.ask`, и языковая строка остаётся последней;
  - у Маши `onProgress` даёт шаг `product`.
- Контроллер: `ui` принимается только со строгими `true`.

**Фронт (vitest):**
- `askBlock.test.ts`: целый блок, недописанный при стриминге, битый JSON (показывается текстом), мягкие пределы, несколько блоков, варианты открывающей строки.
- `askAnswer.test.ts`: сборка ответа (один вопрос, несколько, свой вариант) и обратная подсветка.
- `AskCard.test.tsx`: одиночный выбор уходит по нажатию, множественный — по кнопке, карточка неактивна после ответа или во время хода.
- `turnActivity.test.ts`: склейка одинаковых шагов, отметка «сделано» по следующему шагу, тексту и концу хода, ход без шагов не оставляет строки.

**Вручную на test.linkeon.io:**
- «Найди свежие новости про …» — появляются шаги поиска, после ответа сворачиваются.
- «Напиши поздравление коллеге» — приходит карточка, ответ уходит, карточка гаснет.
- Перезагрузка страницы — карточка восстановилась и неактивна.

## Выкат

Обычный `deploy.sh`: бэк, затем фронт, test → smoke → prod. Порядок безопасен в обе стороны: старый фронт `ui` не шлёт и ничего нового не получает, а новый фронт на старом бэке просто не видит шагов и карточек. Релей не трогаем.

## Вне объёма

- Кнопки вопросов в TG-боте (inline-клавиатура) и отрисовка карточки во Flutter.
- Хранение шагов в базе и их показ после перезагрузки.
- Результаты и ошибки инструментов (✓/✗ по факту). Для этого релей должен пересылать `tool_result`, а это ручной выкат и рестарт с потерей сессий.
- Показ содержимого размышлений модели.
