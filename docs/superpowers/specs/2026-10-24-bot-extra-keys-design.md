# Дополнительные ключи бота и каркас под задачи по расписанию

Дата: 24.10.2026. Объём одобрен владельцем в чате («делай доработку»).

## Зачем

Продавец на Озоне (запрос 24.10) хочет бота-продукт: раз в день забирать данные
через Seller API и Performance API Озона и присылать владельцу отчёт в Telegram.
Платформа такого бота потянет: бот работает круглосуточно (сна по простою нет,
только по неуплате аренды или блоку), исходящий HTTPS из контейнеров открыт
(`DOCKER-USER` пуст), Seller API и Performance API с машины `clients` отвечают.
Но собрать бота нельзя:

1. **Ключи стороннего API положить некуда.** Форма шлёт только `BOT_TOKEN`. Бэк
   принимает до 64 секретов, но только при заведении и только прямым вызовом.
   Ключ, вставленный в чат правки, оседает в `product_turns.prompt`, первыми 60
   символами — в сообщении коммита, а раннер делает `git add -A`, и `.gitignore`
   в каркасе нет — то есть ключ уезжает и в резервную копию.
2. **Расписание.** Планировщика нет, таймер живёт только в `server.js`. Процесс
   перезапускается после каждой правки и при обновлении образа, часы контейнера
   идут по UTC. Инструкция каркаса (`CLAUDE.md`) об этом молчит, и ассистент
   правок почти наверняка напишет `setInterval` на сутки.

Попутно найдено: имена секретов сервер с занятыми не сверяет — это делает только
агент хоста. Имя вроде `PORT` сервер принимает, продукт записывается, а заведение
падает в `failed` уже на машине продуктов.

## Что делаем

1. **Форма бота — блок «Дополнительные ключи».** Пары «имя — значение», значение
   скрытым полем. Уходят в `secrets` вместе с `BOT_TOKEN`. Проверка на месте:
   форма имени переменной, длина, занятые имена, `BOT_TOKEN`, повтор, пустое
   значение.
2. **Занятые имена — одни на хосте, на сервере и в форме.** К прежним десяти
   добавляются имена, которые меняют поведение процессов платформы в
   контейнере. Окружение у раннера, ассистента правок (`claude`), pm2 и git
   общее с продуктом:
   - точные: `SHELL`, `USER`, `BASH_ENV`, `ENV`, `HTTP_PROXY`, `HTTPS_PROXY`,
     `ALL_PROXY`, `NO_PROXY`;
   - семейства: `ANTHROPIC_*` и `CLAUDE_*` — ассистент правок
     (`ANTHROPIC_BASE_URL` увёл бы его запросы вместе с OAuth-токеном на чужой
     адрес), `NODE_*` кроме `NODE_ENV`, `NPM_CONFIG_*`, `LD_*`, `GIT_*`, `PM2_*`,
     `SSL_*`.

   Сравнение без учёта регистра: `https_proxy` и `npm_config_registry` читают
   и в нижнем регистре.
3. **Каркас продукта (обе формы).**
   - `.gitignore`: `data/`, `.env`, `.env.*`, `node_modules/`.
   - Разделы `CLAUDE.md`:
     - «Ключи и пароли» — имена ключей владельца (без значений). Ключи брать
       только из `process.env`, окружение не печатать (вывод команд уходит в
       журнал правки), ключ из текста правки в код не вставлять.
     - «Данные между перезапусками» — каталог `data/`.
     - «Задачи по расписанию» — перезапуски, UTC, `Intl.DateTimeFormat` с
       `timeZone`, дата последнего запуска в `data/`, догон один раз, ошибки
       внутри.
   - У бота ещё «Кому бот отвечает»: данные владельца — только владельцу.
4. **Инструмент `manage_product`.** Ключи, токены и пароли в текст правки не
   вписывать. Ключи бота задаются при создании, сменить их после пока нельзя.

## Чего не делаем (пока)

- **Смена и добавление ключей после заведения.** Нужен новый вид задания у
  агента хоста — пересоздать контейнер с новым окружением. Отдельной задачей.
- **Ключи у сайта в форме** — спроса нет; бэк их и так принимает.
- **Планировщик платформы.**

## Решения по умолчанию (была явная рекомендация)

- **Имена ключей в `CLAUDE.md` — списком моноширинных имён, а не огороженным
  блоком.** Имя ограничено `[A-Za-z0-9_]`, строку или разметку из него не
  собрать. Ограда в документе остаётся одна — блок названия продукта; это
  сторожат тесты каркаса.
- **Значения в каркас не попадают вовсе.** Имя не по форме переменной не
  попадает тоже: вторая линия после `validateSecrets`.
- **Значения обрезаются по краям, как токен.** Поле скрытое (`type=password`),
  перевода строки в нём не бывает.
- **В форме не больше 63 дополнительных ключей** — 64 вместе с `BOT_TOKEN`,
  потолок сервера.
- **Добавленная и не заполненная строка не отправляется и ошибкой не
  считается.**
- **После удачного создания строки ключей стираются из состояния формы**, как и
  токен.
- **Разделы про ключи, данные и расписание — в обоих каркасах.** Механика
  перезапусков и окружения у сайта та же, а запрет печатать окружение бережёт и
  токен платформы.

## Соответствие концепции

Концепция (`linkeon-launcher/docs/superpowers/specs/2026-08-04-launcher-assistant-concept-design.md`,
§2.5) говорит о том, что из жизни пользователя уходит в облако. Ключи
стороннего сервиса — не биография и не выводы о человеке. В облако они уходят
явным действием самого пользователя: он вписывает их в форму продукта, который
по замыслу работает на нашей машине.

Минимизация. Ассистент правок получает в инструкции только имена ключей.
Значения не должны попадать ни в чат, ни в историю правок, ни в git, ни в журнал
правки — отсюда запрет печатать окружение.

Тексты формы честные. «Хранятся зашифрованными» — правда. Обещания «ассистент
их не видит» нет: в контейнере ключи видны как переменные окружения, и спека
provisioning говорит это прямо (стр. 114). Пользователю сказано, чего делать
не надо: присылать ключи в чат.

## Выкат

Каркас и список имён лежат в `product-runner/src/host/`. Этот код — и агент
хоста, и часть хеша образа раннера: `CTX_PATHS` в `product-image-roll.sh`
включает `src`. Поэтому PHASE 4 пересоздаст контейнеры всех продуктов
(секунды на контейнер). Катить, когда нет живых правок и чата продуктов.

Новые разделы `CLAUDE.md` и `.gitignore` получат только продукты, заведённые
после выката. У существующих чекаутов ничего не меняется.
